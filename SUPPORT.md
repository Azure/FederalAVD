# Support

## Questions and Support

Start with the [documentation](docs/README.md) and
[troubleshooting guide](docs/troubleshooting.md). GitHub Copilot Chat in this repository also has
FederalAVD-specific context and can help identify an existing parameter, deployment pattern, or
known failure before an issue is opened.

FederalAVD is an open-source project and does not replace support provided through an Azure support
plan. Use Microsoft Azure Support for subscription-specific incidents, service outages, quota
requests, or issues that require access to private tenant and resource data.

## Bugs and Feature Requests

[GitHub Issues](https://github.com/Azure/FederalAVD/issues) is the authoritative backlog for bugs
and future feature work. Search open and closed issues before creating a new item, then use the
appropriate bug or feature-request form.

Each future feature issue should identify:

- The problem or gap and affected deployment area.
- Target Azure clouds.
- Proposed scope and explicit non-goals.
- Observable acceptance criteria.
- Dependencies and related documentation or issues.
- Security, identity, networking, compliance, and air-gapped implications.

Use the `enhancement` label for feature work. Use milestones to communicate a planned release only
after maintainers have scheduled the work. An open issue without a milestone records a candidate
feature, not a delivery commitment.

## Design Notes and Roadmaps

Keep detailed design constraints near the component that owns the behavior, usually in its README
or documentation page, and link that material from the issue. GitHub Issues remains the source of
truth for status, ownership, priority, and completion.

Do not maintain a duplicate checklist of individual issues in documentation. Add a repository-level
roadmap only when maintainers need to communicate a curated sequence of planned releases; roadmap
entries should link back to their authoritative issues.
